# 手机 ↔ 手表 蓝牙文本同步协议 v1

> 实现位置：`_common/src/com/astrbot/watchsync/common/Proto.java`（两端共享），
> 手机端 `SyncService`（服务端），手表端 `SyncService`（客户端）。

## 1. 传输层

| 项 | 值 |
| --- | --- |
| 承载 | 经典蓝牙 RFCOMM（SPP 风格），复用手机与手表的系统配对，无需重新配对 |
| 服务 UUID | `7a1f3c2e-5b4d-4a6e-9f80-2c3d4e5f6a7b` |
| 连接方向 | **手机监听**（前台服务持 `listenUsingRfcommWithServiceRecord`），**手表主动连接**（手表打开 app 时） |
| 安全 | 手表优先用安全 RFCOMM（走系统配对的链路密钥加密），失败退非安全 RFCOMM 兜底 |
| 帧格式 | `4 字节大端长度 + UTF-8 JSON 正文`，长度上限 1,000,000 字节 |
| 重试 | 手表断开后每 10 秒重连；手机蓝牙关闭/恢复时自动重启监听 |

## 2. 同步模型

**手机是权威端**（列表 + 离线队列都在手机），手表只是缓存镜像 + 操作入口：

1. 手机随时可发文本：写进手机端权威列表；若手表当前在线则立即推送，否则等手表下次连接时随全量列表送达（无独立队列，列表本身就是队列）。
2. 手表打开 app → 连上手机 → 发 `hello`（若有离线期间积压的 `ops` 则紧随其后发 `ops`）。
3. 手机每收到一条消息（`hello` / `ops`），或本端有新增，都回推一次**全量** `list`（列表 ≤100 条非置顶 + 全部置顶，全量推送免去增量同步/冲突处理）。
4. 手表收到 `list` 才认为 pending ops 已落账（此时清空本地 ops 队列）——连接中途断开也不会丢操作。
5. 手表离线期间做的删除/置顶：先本地乐观生效 + 存入 pending 队列，连上后回放。

## 3. 消息定义

### 3.1 `hello` — 手表 → 手机（连接后第一条）

```json
{"t": "hello", "name": "OPPO Watch SE"}
```

### 3.2 `ops` — 手表 → 手机（操作回放，可多条打包）

```json
{
  "t": "ops",
  "ops": [
    {"op": "del", "ids": ["<uuid>", "..."]},
    {"op": "pin", "ids": ["<uuid>"], "on": true}
  ]
}
```

- `op=del`：删除指定 id 的消息。
- `op=pin`：`on=true` 置顶 / `on=false` 取消置顶。
- 操作幂等（按 id 匹配，找不到则忽略），重复回放安全。

### 3.3 `list` — 手机 → 手表（全量权威列表，每次都推全部）

```json
{
  "t": "list",
  "items": [
    {"id": "<uuid>", "text": "取件码 3-2-8888", "pinned": false, "ts": 1758200000000}
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 消息唯一 id（手机端生成 UUID） |
| `text` | string | 文本内容（手机端截断至 8000 字符） |
| `pinned` | bool | 是否置顶 |
| `ts` | long | 手机端接收时间（UTC 毫秒） |

### 3.4 排序与保留策略

- 排序：`pinned` 优先，其余按 `ts` 倒序（两端一致）。
- 手机端保留：置顶全保留；非置顶最多 100 条，超限淘汰最旧。

## 4. 前向兼容

两端都忽略未识别的消息类型 / 字段，未来扩展（如已读回执、加密）只需新增 `t` 值。
若手表端 RFCOMM 被系统限制（ColorOS Watch 8.1 实测无碍的预案）：传输层可换成
BLE GATT（手机做 GATT Server），帧格式与消息定义不变。
